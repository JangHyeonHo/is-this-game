# 문서 규칙

이 저장소의 문서는 사람 한 명과 에이전트가 번갈아 읽는다. 대화는 매번 초기화되고
기억은 남지 않으므로, 문서가 남기는 것이 곧 다음 판단의 근거가 된다. 그래서 문서가
낡거나 뒤섞이면 잘못된 결론이 문서를 근거로 나온다.

이 문서는 그것을 막기 위한 규칙이다. 어느 문서가 무엇을 답하고, 무엇을 고쳐도 되고,
어떻게 쓰는지를 정한다. 새 문서를 쓰거나 기존 문서를 고치기 전에 읽는다.

각 규칙이 무엇을 막는지는 규칙 옆에 붙어 있고, 조사한 근거는 §6에 모았다.

---

## 1. 세 종류를 섞지 않는다

문서는 답하는 질문이 서로 다르다. 한 파일에 섞으면 갱신 규칙이 충돌한다 —
현재 상태는 덮어써야 하고 결정 이력은 덮어쓰면 안 되기 때문이다. 그래서 종류를
파일 단위로 가른다.

| 종류 | 답하는 것 | 갱신 | 이 갱신 규칙이 지키는 것 |
|---|---|---|---|
| **명세** | 지금 무엇인가 | **덮어쓴다.** 폐기된 것은 지운다 | 현재 상태를 한 곳에서 본다 |
| **결정 기록** | 왜 · 누가 정했나 | **추가만 한다.** 고치지 않는다 | 그때 무엇이 사실이었는지 알 수 있다 |
| **측정 기록** | 얼마로 나왔나 | **추가만 한다** | 같다 |

명세에 묘비를 세우지 않는다. "여기에 X가 있었다"는 결정 기록의 몫이다. 폐기된 설계를
명세에 인용해 두면 그것이 오답의 근거가 된다 (§6.2).

## 2. 어느 문서를 언제 보나

질문을 문서로 바로 옮기기 위한 표다. 이 표가 있으면 여러 문서를 뒤지지 않고
한 곳만 열게 된다.

| 알고 싶은 것 | 볼 곳 |
|---|---|
| 그 기능 있나 | [04-implemented.generated.md](04-implemented.generated.md) — 코드에서 생성. 없으면 없는 것 |
| 지금 게임이 어떻게 굴러가나 | [01-game-design.md](01-game-design.md) — 명세 |
| 코드가 어떻게 나뉘어 있나 | [02-architecture.md](02-architecture.md) — 설계서 |
| 그 수치가 어디 있나 | [03-formulas.md](03-formulas.md) — 코드 위치 지도 |
| 왜 · 누가 정했나 | [07-decisions.md](07-decisions.md) — 결정 기록 |
| 왜 그 숫자인가 | [08-balance-log.md](08-balance-log.md) — 측정 기록 |
| 왜 아직 없나 | [05-gaps.md](05-gaps.md) |
| 만들면 안 되는 건가 | [00-charter.md](00-charter.md) §4 |
| 기술 선택 근거 | [adr/](adr/) |

반대 방향도 필요하다. 무언가를 한 뒤 어디에 남길지 헷갈리면 갱신이 빠지고,
빠진 갱신이 곧 낡은 문서가 된다.

| 무엇을 했나 | 어디에 쓰나 |
|---|---|
| 규칙을 구현했다 | 명세를 덮어쓴다. 낡은 서술은 지운다 |
| 무언가 결정됐다 | 결정 기록에 항목을 추가한다. 기존 항목은 고치지 않는다 |
| 결정이 바뀌었다 | 항목을 추가하고, 옛 항목의 **상태만** `대체됨`으로 바꾸고 서로 링크한다 |
| 수치를 측정했다 | 측정 기록에 추가한다 |
| 공개 타입을 바꿨다 | `UPDATE_INVENTORY=1 dotnet test --filter SystemInventory` — 같은 커밋에 |
| 코드에서 수치를 바꿨다 | 문서에 값을 복사하지 않는다. 코드가 정본이다 |
| 없던 기능을 만들었다 | [05-gaps.md](05-gaps.md)에서 그 줄을 지우고 명세에 쓴다 |
| 제약을 풀었다 · 원인을 알아냈다 | [05-gaps.md](05-gaps.md)에서 그 줄을 지운다. 쌓이면 낡은 걱정 목록이 된다 |

## 3. 표기 — 누가 정했는가

같은 문서 안에 사람이 정한 것과 에이전트가 제안한 것이 섞인다. 구분이 없으면 제안이
결정으로 읽히고, 사람이 기억하지도 못하는 결정을 근거로 작업이 진행된다.
항목마다 표기를 달아 그것을 막는다.

| 표기 | 뜻 | 다룰 때 |
|---|---|---|
| **[확정]** | 수치·규칙까지 정해짐 | 구현 착수 가능 |
| **[방향]** | 방향만 합의. 세부 미정 | 착수 불가. [확정]으로 올리지 않는다 |
| **[검토중]** | 판단 대기 | 착수 불가 |
| **[제안]** | 에이전트 안. 승인된 적 없음 | 결정으로 인용하지 않는다 |
| **[대체됨]** | 뒤의 항목이 대체함 | 그 항목을 본다 |

규칙 둘.

- 절 전체에 "표기 없는 항목은 전부 [확정]"이라고 선언하지 않는다. 무표기 한 줄이 자동으로
  확정이 된다. 항목마다 표기를 단다.
- [검토중]은 **판단이 필요한 것**에만 쓴다. 만들거나 측정할 일은 [검토중]이 아니라
  [05-gaps.md](05-gaps.md)의 할 일이다. 섞으면 판단 대기 목록이 부풀어
  정작 판단이 필요한 항목이 묻힌다.

## 4. 구성 — 무엇을 위한 글인지 드러나게 쓴다

규칙만 나열된 문서는 다음 사람이 되돌린다. 그 규칙이 무엇을 막고 있는지 모르면
불편한 제약으로만 보이기 때문이다. 반대로 목적을 절마다 소제목으로 선언하면
분량만 늘고 읽히지 않는다. 그래서 목적은 **서술 안에 녹인다.**

- **문서에는 그 문서의 내용만 쓴다.** 그 문서를 어떻게 갱신하고 무엇을 적지 말아야
  하는지는 문서의 내용이 아니라 이 파일과 `CLAUDE.md`의 내용이다. "여기 적지 않는다",
  "추가만 한다", "지우는 것이 유지 방법이다" 같은 문장을 본문에 두지 않는다.
- 문서 첫머리에 **무엇을 다루는 글인지** 쓴다. 제목만으로는 알 수 없다. 두세 문장이면
  충분하고, 길어지면 일기가 된다.
- 절은 규칙을 쓰고, 그 규칙이 **무엇을 지키거나 막는지**를 한 줄로 이어 붙인다.
  `## 1. 이 절의 목적` 같은 소제목을 만들지 않는다.
- 표에는 규칙 옆에 그 규칙의 효과를 두는 칸을 둔다. 표만으로 이유가 서지 않으면
  표 앞에 한두 문장을 둔다.
- **이력으로 본문을 더럽히지 않는다.** 무엇이 취소됐고 무엇이 있었는지는 이 글로 답하지
  않는다. 이력을 남길 곳은 정해져 있다 — 결정은 [07](07-decisions.md),
  측정은 [08](08-balance-log.md), 나머지는 git이다. 본문에는 **링크만** 둔다.
  같은 규칙을 코드 주석에도 적용한다.
- 근거가 길면 본문에 풀지 않고 결정 기록으로 링크한다.

## 5. 문체

문서는 규정문이다. 이야기가 아니다. 사담과 회고가 섞이면 분량이 두 배가 되면서
정작 규칙이 어디인지 흐려진다.

| 쓰지 않는다 | 쓴다 |
|---|---|
| 사람 (`주인님`, `제가`, `우리가`) | 주어 없는 규정문 |
| 이력 (`예전에는`, `폐기됐다`, `사고가 났다`) | 지금 규칙만. 이력은 결정 기록에 |
| `~의 경우` | `~면`, `~일 때` |
| `~에 대해서`, `~에 관해서` | 조사로 처리 |
| `~하는 것이 가능하다` | `~할 수 있다` |
| `~해 둔다` | `~한다` |
| `~적(的)` | 구체적인 말 |
| `~라고 하는` | `~인`, `~라는` |
| 문장마다 굵게 | 절당 한두 곳 |

- 종결은 명세·규칙 문서에서 `~한다`로 통일한다. 존댓말을 쓰지 않는다.
- 한 문장에 한 규칙. 짧게 끊는다.

## 6. 이 구조의 근거

아래는 이 규칙들을 정할 때 조사한 것이다. 규칙을 바꾸려면 여기부터 본다 —
근거를 모르고 바꾸면 이미 알려진 실패를 다시 겪는다.

### 6.1 한 문서에 여러 목적을 담으면 셋 다 못 쓴다 — Diátaxis

문서는 **행동/지식 × 학습/작업** 두 축에서 네 종류로 갈린다 — 튜토리얼 · 사용법 ·
레퍼런스 · 설명. 답하는 질문이 다르므로 섞으면 어느 독자도 만족시키지 못한다.
Django · Canonical · Cloudflare가 쓴다.

적용: 명세(레퍼런스)와 결정 기록(설명)을 분리한다 (§1).

### 6.2 긴 컨텍스트는 정확도를 떨어뜨린다 — context rot

Chroma가 프런티어 모델 18종을 측정한 결과 전부 입력이 길어질수록 나빠졌다.

- 한계 근처가 아니라 **모든 구간**에서 떨어진다. 100만 토큰 창에서도 5만 토큰에서 발생한다
- **U자 곡선** — 앞뒤는 잘 보고 가운데는 정확도가 30% 이상 낮다
- **의미가 비슷하지만 관련 없는 내용이 능동적으로 오답을 유도한다** (distractor interference).
  길이만으로 설명되는 것보다 더 나쁘다

적용: 명세에서 폐기된 내용을 지운다. 묘비도 두지 않는다. 묘비 자체가 distractor다 (§1, §4).

### 6.3 에이전트 지침은 짧고 사람이 쓴 것이어야 한다 — AGENTS.md / CLAUDE.md

2,500개 이상 저장소 조사 결과.

- **150줄을 넘으면 효과가 줄고** 추론 비용이 20~23% 늘면서 성능은 나아지지 않는다
- **LLM이 생성한 지침 파일은 성능을 떨어뜨린다** — 8개 설정 중 5개에서 성공률이 내려갔고
  과제당 2.45~3.92단계를 더 썼다
- 사람이 쓴, 자명하지 않은 정보를 담은 파일이 더 좋았다
- 구조는 WHAT / WHY / HOW. 세부는 별도 문서로 빼고 링크만 남긴다
- 지침 파일을 린터로 쓰지 않는다. 스타일 규칙은 비싸고 불안정하다

적용: `CLAUDE.md`를 150줄 이하로 유지한다. 스타일은 테스트와 컴파일러가 지킨다.

### 6.4 결정 기록은 고치지 않는다 — ADR

ADR은 추가만 하는 로그다. 승인된 기록은 편집하지 않는다. 결정이 바뀌면 새 기록으로
대체하고 둘을 서로 링크한다. 바뀔 수 있는 것은 상태뿐이다.

고치지 않는 것이 이 모음을 신뢰할 수 있게 만든다. 반년 뒤에 읽어도 그때 무엇이
사실이었는지 알 수 있다.

적용: [07](07-decisions.md)을 추가 전용으로 둔다.

### 6.5 게임 디자인 문서는 짧고, 잘린 기능은 지운다 — GDD

- 처음에 100쪽을 쓰는 것은 안티패턴이다. 즉시 낡고 중요한 결정을 묻는다
- 좋은 GDD는 짧고 검색 가능하며 게임이 바뀔 때 갱신된다. 고정 명세서가 아니다
- 기능이 잘리면 마스터 문서에서 **지운다**. 주석을 달지 않는다
- 1인 개발은 한 쪽, 소규모 팀은 5~15쪽이면 충분하다
- 정해진 뒤에만 세부를 적는다. 잘릴 수 있는 기능을 문서화하지 않는다

적용: 명세를 400줄 이하로 둔다. 안 정한 것은 명세가 아니라 결정 기록에 둔다.

### 6.6 수치는 코드가 정본이다 — spec-driven · 생성 문서

명세와 구현이 갈라지는 것은 부지런히 고쳐서 막는 것이 아니라, 한쪽을 정본으로 정하고
나머지를 생성하거나 검증해서 막는다.

적용 셋.

1. 타입 목록을 생성한다 — [04-implemented.generated.md](04-implemented.generated.md).
   어긋나면 `SystemInventoryTests`가 깨진다
2. 수치는 코드가 정본이다 — [03](03-formulas.md)은 값이 아니라 파일 위치만 적는다.
   틀린 값은 사람을 속이지만 틀린 경로는 즉시 드러난다
3. 규칙은 테스트가 지킨다. "기억하라"로는 지켜지지 않는다
