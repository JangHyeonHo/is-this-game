# 02. 소프트웨어 설계

Guildwright의 코드가 어떻게 나뉘어 있고, 각 부분이 무엇을 맡고, 왜 그런 모양인지를 적는다.
[01-game-design.md](01-game-design.md)가 게임의 규칙을 적는다면, 이 문서는 그 규칙을
담는 그릇의 구조를 적는다. 코드를 고치기 전에, 새 기능을 어디에 넣을지 정할 때 본다.

여기 적힌 것은 확정된 설계만이다. 아직 없는 것은 [05-gaps.md](05-gaps.md)에 있다.

## 1. 전체 구조 — 코어와 껍데기

프로젝트는 셋으로 나뉜다.

```
src/Guildwright.Core      게임 규칙 전부. 순수 C#, 외부 의존 없음
src/Guildwright.Console   콘솔 프론트엔드. 코어를 불러서 텍스트로 보여준다
tests/                    xUnit 테스트. 코어만 대상으로 한다
```

**게임 엔진은 아직 없고, 코어는 엔진을 모른다.** Unity로 가든 Godot으로 가든 코어는
그대로 두고 껍데기만 바꾼다. 지금의 콘솔이 그 첫 번째 껍데기이고, 엔진이 정해지면 두 번째
껍데기가 된다. 이 결정의 배경은 [adr/0001](adr/0001-engine-agnostic-core.md)에 있다.

이 구조가 지키는 것은 두 가지다. 엔진 선택을 미룰 수 있고(M2에서 정한다), 게임 규칙 전체를
엔진 없이 테스트와 시뮬레이션으로 돌릴 수 있다.

## 2. 코어의 순수성

코어는 바깥 세계를 건드리지 않는다.

| 금지 | 대신 쓰는 것 |
|---|---|
| 파일 입출력 | 껍데기가 한다. 코어는 값을 주고받기만 한다 |
| `DateTime.Now` 등 현재 시각 | 게임 내 달력(`Calendar`)만 쓴다 |
| `static` 가변 상태 | 상태는 인스턴스에 담고, 공유 데이터는 읽기 전용 표로 둔다 |
| `System.Random` 직접 생성 | 주입받은 `IRandomSource` |
| `string.GetHashCode()` | FNV-1a 안정 해시 (실행마다 값이 같다) |

이 다섯 가지는 전부 같은 이유에서 나온다 — **같은 입력이면 언제 어디서 돌려도 같은 결과가
나와야 한다.** 밸런스를 배치 시뮬레이션으로 잡는 프로젝트라서, 재현이 안 되는 코어는
밸런스 판단의 근거를 통째로 무너뜨린다.

## 3. 결정론 — 난수와 순서

재현성이 실제로 깨지는 지점은 난수와 순회 순서다. 그래서 이 둘을 설계로 못 박았다.

**난수.** 모든 난수는 `Rng/IRandomSource`를 통해 나온다. 구현은
`DeterministicRandom`(xoshiro256\*\* + SplitMix64 시드 확장)이고, `Fork(label)`로 스트림을
가지 쳐서 시스템마다 독립된 난수열을 쓴다. 라벨을 해시할 때 FNV-1a를 쓰는 이유는
`string.GetHashCode()`가 실행마다 다른 값을 주기 때문이다.

**순서.** `Dictionary`와 `HashSet`의 순회 순서는 보장이 없으므로 로직에 쓰지 않는다.
순서가 결과에 영향을 주는 곳은 전부 `Ordinal` 기준으로 정렬해 놓았다.

**보정 계산.** 여러 보정이 겹칠 때는 덧셈으로 모아서 마지막에 한 번 곱한다. 곱셈을
누적하면 적용 순서에 따라 결과가 달라진다.

**관전 무간섭.** 전투 기록을 켜든 끄든 난수 소비가 같다. 지켜보는 것이 결과를 바꾸면
"기록을 껐더니 이겼다" 같은 재현 불가능한 버그가 된다.

새 시스템에는 재현성 테스트(같은 시드로 두 번 돌려 같은 결과)를 함께 넣는다.
`DeterministicRandomTests`와 `FloatingPointStabilityTests`가 기반을 지킨다.

## 4. 모듈 구성

코어는 아홉 개 네임스페이스로 나뉜다. 대체로 아래에서 위로 의존한다 — `Rng`가 바닥이고,
그 위에 도메인(모험가·무기·스킬), 그 위에 활동(전투·훈련·파견·파티), 맨 위에 도구가 있다.

| 모듈 | 맡는 것 | 중심 타입 |
|---|---|---|
| `Rng` | 결정론적 난수 | `IRandomSource` · `DeterministicRandom` |
| `Adventurers` | 모험가 — 능력치 · 성장 곡선 · 평가서 · 나이 | `Adventurer` · `GrowthProfile` · `Appraiser` |
| `Weapons` | 무기 표 · 장착 4칸 · 숙련도 · 적성 | `Weaponry` · `Loadout` · `WeaponProficiency` |
| `Skills` | 직업 표 · 스킬 표 | `Jobs` · `SkillBook` |
| `Combat` | 자동 전투 — 라운드 · 피해 계산 · AI · 상태 효과 | `BattleResolver` · `TacticalBrain` · `Combatant` |
| `Training` | 달 단위 훈련 — 활동 · 피로 · 예보 | `TrainingYearSession` · `TrainingForecaster` |
| `Careers` | 의뢰 · 파견 · 결산 · 멘토 | `Contract` · `ContractBoard` · `DeploymentSession` · `CareerSimulator` |
| `Parties` | 등급 · 가상/정규 파티 · 장부 | `Rank` · `Party` · `PartyLedger` |
| `Balance` | 배치 시뮬레이터 | `BatchSimulator` · `TrainingSimulator` |

경계가 하나 있다. **육성 세계와 전투 세계는 `CombatantFactory` 한 곳에서만 만난다.**
모험가(육성의 단위)를 전투원(전투의 단위)으로 바꾸는 변환이 여기 모여 있어서, 육성 결과가
전투에 어떻게 반영되는지 볼 때 이 파일 하나만 보면 된다.

정보 은닉도 한 곳에 모여 있다. 성장 곡선(`Adventurer.Growth`)은 게임의 핵심 비밀이므로
화면에 직접 내보내지 않고, `Appraiser`가 만드는 부정확한 추정만 껍데기에 준다.

## 5. 규칙과 상태의 분리

도메인 모델은 가능한 한 불변으로 두고, 변경은 새 인스턴스를 반환한다. 규칙은 상태를
갖지 않는 정적 순수 함수에 가깝게 둔다 — `DerivedStats`(능력치 계산), `DamageModel`(피해
계산), `PartyFormation`(조합 판정)이 그 형태다. 규칙이 순수 함수면 테스트가 입력과 출력만
보면 되고, 시뮬레이션에서 같은 규칙을 수천 번 불러도 상태 오염이 없다.

## 6. 콘텐츠는 코드가 아니라 데이터다

콘텐츠 종류가 늘어도 코드 경로는 늘지 않게, 기전과 이름을 분리해 놓았다.

| 콘텐츠 | 코드에 있는 것 | 데이터 표에 있는 것 |
|---|---|---|
| 무기 | 위력·속도·사거리를 합산하는 계산 | 검·도끼·활… 각각의 수치 (`Weaponry.Table`) |
| 직업 | 요구 숙련 검사, 히든 직업 해금 | 직업마다의 요구 숙련·슬롯·자격 (`Jobs.Table`) |
| 스킬 | 행동 실행 경로 | 스킬마다의 마나·쿨다운·요구 무기 (`SkillBook.Table`) |
| 상태 효과 | 기전 8종 (지속 피해, 행동 불가 …) | 이름 26개와 각각의 프로필 |
| 의뢰 | 완료 판정 4형태 (토벌·지킴·수집·발견) | 의뢰 이름 풀, 출처, 기간 |

새 무기·직업·스킬·상태 효과를 추가하는 일은 표에 한 줄을 넣는 일이다. `switch`가
늘어난다면 축을 잘못 잡은 것이다.

밸런스 수치는 전부 코드의 데이터 표·상수에 있고, 문서에는 복사하지 않는다. 어느 파일에
어떤 값이 있는지는 [03-formulas.md](03-formulas.md)가 안내한다.

## 7. 테스트 전략

코어 코드는 테스트 없이 병합하지 않는다. 테스트는 세 층이다.

1. **규칙 테스트** — 각 시스템의 규칙이 명세대로 움직이는지. xUnit,
   이름은 `메서드_상황_기대결과` 형식
2. **설계 대조 테스트** (`DesignConformanceTests`) — 구현이 결정 기록의 확정 사항과
   어긋나지 않는지. 규칙이 코드 리뷰가 아니라 테스트로 지켜진다
3. **재현성 테스트** — 같은 시드로 두 번 돌려 같은 결과가 나오는지

여기에 스냅숏 장치가 하나 있다. 공개 타입 목록을 어셈블리에서 생성해
[04-implemented.generated.md](04-implemented.generated.md)로 두고, 코드와 어긋나면
`SystemInventoryTests`가 깨진다. "무엇이 구현되어 있는가"라는 질문에 낡은 답이 나가는
것을 테스트가 막는다.

Docker 빌드는 빌드 단계에서 전체 테스트를 돌린다. 테스트가 깨진 이미지는 만들어지지 않는다.

## 8. 껍데기 — 콘솔

`Guildwright.Console`은 코어를 달 단위 루프로 돌리는 텍스트 프론트엔드다. 매달 게시판을
보여주고, 모험가마다 훈련/휴식/의뢰/전직을 입력받고, 파견과 전투 결과를 출력한다.
배치 시뮬레이션 모드(`-- sim`)도 여기서 실행한다.

콘솔에는 게임 규칙이 없다. 입력을 코어 호출로 바꾸고 결과를 문자열로 바꾸는 것까지만
한다. 규칙 검사를 콘솔에 두면 다음 껍데기(엔진 UI)에서 그 검사가 사라진다.
