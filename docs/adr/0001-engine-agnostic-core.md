# ADR 0001. 게임 코어를 엔진 독립적인 순수 C#으로 만든다

- **상태:** 채택
- **일자:** 2026-07
- **관련:** [00-charter.md](../00-charter.md), [02-research-tech.md](../02-research-tech.md)

## 맥락

엔진을 Unity로 할지 Godot으로 할지 정해야 했습니다. 리서치 결과는 이랬습니다.

**Godot 4.7 + C# 쪽 근거**
- 씬/리소스 파일(`.tscn`/`.tres`)이 사람이 읽는 텍스트 → AI 에이전트가 에디터 없이 읽고 수정 가능
- `godot --headless --script`로 CLI 자동 테스트 가능 → 에이전트 자율 루프 구성 가능
- MIT 라이선스. 매출과 무관하게 요금·정책 리스크 0
- 상업적 검증 완료: 2025-26년 Steam에 2,864편(신규의 8~10%), Brotato 1,000만 장, Backpack Battles $5.2M

**Unity 6.3 LTS + C# 쪽 근거**
- Unity C#은 **모든 엔진 중 LLM 훈련 데이터가 가장 많음**. 반대로 Godot은
  LLM이 Godot 3와 4 문법을 섞는 환각이 실제로 보고됨 (문법은 유효한데 조용히 아무것도 안 함)
- 에셋스토어 80,000개+ vs Godot 약 3,000개
- **개발자가 이미 익숙하고 구매한 에셋이 있음.** 리서치는 첫 상업작 실패 원인으로
  "엔진 심화 학습의 숨은 비용"을 명시적으로 지목했다
- Unity MCP가 2026년 공식화됨 (`com.unity.ai.assistant`) — AI 격차가 2025년 대비 실제로 줄었다
- UI Toolkit(UXML/USS)은 텍스트 기반이라 UI 중심 게임에서는 Unity도 에이전트 친화적
- $200,000 매출까지 무료, 스플래시 제거 가능

**Unity 쪽의 남은 약점**
- Unity MCP는 **에디터 실행이 전제** → 헤드리스 자율 루프에 부적합.
  Unity 공식 문서도 "베타이니 프로덕션 워크플로에 바로 넣지 말라"고 명시
- 씬/프리팹이 fileID + GUID YAML이라 에이전트에게 불투명

**실측 확인 (2026-07, 이 프로젝트의 원격 개발 컨테이너에서)**

| 항목 | 결과 |
|---|---|
| Godot 4.4 mono 다운로드 → 헤드리스 실행 | ✅ `4.4.stable.mono.official` |
| .NET SDK | ✅ 8.0.129 설치 성공 |
| Unity 다운로드 | ❌ egress 정책상 403 차단 |

## 결정

**엔진 선택을 지금 하지 않는다. 대신 게임 코어를 엔진 의존성이 0인 순수 C# 라이브러리로 분리한다.**

```
src/Guildwright.Core/       엔진 참조 0. 육성 · 전투 · AI · 절차적 생성 · 길드 경제
tests/Guildwright.Core.Tests/  xUnit
─────────────────────────── (경계)
Game.Unity/ 또는 Game.Godot/   렌더링 · 입력 · UI · 연출 · 사운드만
```

**엔진 결정은 M1(코어 프로토타입) 완료 후로 미룬다.**
그 시점에는 콘솔에서 텍스트로 육성 런과 전투가 돌아가므로,
양쪽에 얇은 뷰를 붙여 실제로 비교할 수 있다.

## 근거

1. **이 게임은 코어 비중이 압도적이다.** 육성 시뮬 + 자동 전투 + 길드 경제는
   렌더링이 아니라 **규칙이 본체**다. 전체 코드의 60~70%가 코어에 들어간다.
2. **그 60~70%를 엔진 없이 개발·테스트할 수 있다.** 원격 세션의 AI 에이전트가
   코어 전체를 담당할 수 있고, 이는 엔진 선택과 무관하다.
3. **AI 코드 기술부채의 유일한 실효 방어책이 자동 테스트다.**
   AI 도구 도입 후 기술부채 30~41% 증가, 코드 중복 48% 증가,
   90일차에 스프린트 캐파의 20~30%를 AI 생성 코드 유래 버그에 소모한다는 실측치가 있다.
   순수 C# 코어는 `dotnet test`로 이 방어선을 공짜로 얻는다.
4. **AI가 잘하는 일과 사람이 해야 하는 일이 파일 경계로 갈린다.**
   에이전트는 코어(순수 로직, 테스트 가능)를, 사람은 엔진 레이어(게임 필, 연출, 체감)를 맡는다.
5. **결정이 되돌릴 수 있게 된다.** 엔진을 바꿔도 코어는 그대로다.
   1인 개발에서 되돌릴 수 없는 결정의 수를 줄이는 것 자체가 리스크 관리다.
6. **자동 전투 게임의 밸런싱은 배치 시뮬레이션으로 한다.**
   엔진 없이 코어만으로 10,000회 전투를 돌려 승률 분포를 뽑을 수 있어야 하고,
   이 구조가 그걸 가능하게 한다.

## 결과

**긍정**
- 엔진 학습 비용을 프로젝트 후반으로 미룰 수 있다
- 밸런스 회귀 테스트와 배치 시뮬레이션이 처음부터 가능하다
- 원격 세션에서 에이전트가 할 수 있는 일의 범위가 최대가 된다

**부정 / 비용**
- 코어와 뷰 사이의 경계를 설계하고 유지하는 비용이 든다
- 코어에 엔진 타입(`Vector2`, `Color` 등)을 쓰고 싶은 유혹을 계속 거절해야 한다
- "화면에 뭔가 보이는" 시점이 늦어져 동기 부여가 떨어질 수 있다
  → **완화책: M1에 콘솔 UI를 만들어 텍스트로라도 플레이 가능하게 한다**

## 강제 규칙

1. `Guildwright.Core`는 **엔진 어셈블리를 참조하지 않는다.** CI에서 검사한다.
2. 코어는 **부작용이 없어야 한다** — 파일 I/O, 시간, 전역 상태 금지.
   난수는 반드시 주입된 `IRandomSource`로만 얻는다.
3. 코어의 모든 공개 규칙에는 테스트가 있어야 한다. **테스트 없는 코어 코드는 머지하지 않는다.**
